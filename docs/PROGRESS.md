### 2026-09-10 — 설계 검토와 수정

기존 설계·구현을 다시 검토해 다음을 고쳤습니다. 모두 실험 결과를 보기 전의 수정입니다.

- 유실 마스크가 호스트-일 파일 전체에 걸려 있었습니다. 연속 유실의 시작점이 하루 전체에서 균등 추출되므로 평가 구간(약 2시간)을 스치지 않는 시드가 대부분이었고, 그러면 두 방식이 평가 구간에서 지우는 이벤트 수가 달라져 가설의 전제가 무너집니다. 삭제 범위를 평가 구간으로 한정하고 마스크 스키마를 `loss-mask-v2`로 올렸습니다.
- 사례 탐지 판정이 라벨 노드 하나만 넘어도 성립하므로 주비교 유실률에서 포화될 수 있습니다. 고정 라벨 노드 재현율을 공동 1차 지표로 추가하고, 포화 시 어느 지표로 결론을 낼지의 순서를 먼저 고정했습니다.
- 723회 실행의 저장 용량(약 150GB)과 소요 시간을 산출한 적이 없었습니다. 변형 입력 비보관 원칙과 단계별 축소 규칙을 고정했습니다.
- 실행 호스트가 Linux일 가능성이 높은데 `curl.exe`가 하드코딩되어 있었습니다. 받아 둔 파일을 재검증할 경로가 없어 09-20 파일이 manifest에 기록되지 못했고, 실패한 다운로드의 응답 헤더가 재시도 때 덮어써졌습니다. 셋 다 고쳤습니다.
- `data/` 전체가 Git에서 제외되어 선택 다운로드를 재현하게 하는 `index.jsonl`과 `manifest.jsonl`이 재현 패키지에서 빠졌습니다. 대용량 입력은 계속 제외하고 이 기록만 포함하도록 바꿨습니다. 성공 응답 헤더에는 만료된 서명 URL이 들어 있어 계속 제외하며, 실패 기록은 `attempts.jsonl`로 남깁니다.
- 환경 점검 도구가 Windows에서 메모리를 항상 `null`로 보고했습니다. 이 도구는 호스트가 실험을 감당할 수 있는지 확인하려고 만든 것이므로 정확히 그 값이 빠져 있었습니다. Windows 메모리 조회를 추가하고, 조회 결과가 비어 있으면 실패하는 테스트를 넣었습니다.
- 수정한 도구를 실제로 실행해 확인했습니다. 확보한 09-19 로그(5,136,112건)에서 평가 구간 위치를 산출했고, 마스크 생성부터 집계까지 다섯 도구를 명령줄로 연결해 두 유실 방식이 같은 구간에서 같은 개수를 지우는지 확인했습니다.
- 그 측정에서 10% 연속 유실의 실제 삭제 길이가 122분 창 중 9.4분이고 창의 약 92%가 손상되지 않는다는 것을 확인했습니다. 이에 따라 가설을 A-v1(평균 탐지율 차이)에서 **A-v2(시드 간 변동 차이)**로 수정했습니다. A-v1의 평균 비교는 폐기하지 않고 함께 사전 등록합니다. 수정 전후와 이유는 [연구 기반](RESEARCH_FOUNDATION.md)에 있습니다. 추가 실행은 필요하지 않습니다.

### 2026-09-10 — 탐지기 확인과 채점기

- PIDSMaker를 고정 커밋 `ae1e9fd4`로 확보해 문서가 인용만 하던 값을 코드에서 확인했습니다. 세 공격 구간 문자열, `max_val_loss`, `node_evaluation`이 모두 기록과 일치했습니다.
- **시간대 미확인 항목을 해결했습니다.** 설정의 시간 문자열은 `US/Eastern`으로 해석되며 2019년 9월이면 UTC−04:00입니다. OpTC timestamp의 오프셋과 같고, 앞서 수행한 구간 산출도 이 해석이었습니다.
- `max_val_loss`가 검증 경로에서만 임계값을 얻는다는 것을 평가 코드에서 확인했습니다. 테스트 입력의 유실이 임계값을 바꾸지 않습니다.
- 노드 점수를 실행 기록으로 바꾸는 [채점기](../scripts/score_run.py)를 만들었습니다. 분모는 무유실 입력에서 고정한 정답 노드 수이며, 유실로 사라진 정답 노드는 미탐지로 셉니다. 살아남은 노드만으로 계산하면 피해가 큰 조건일수록 재현율이 높아 보이는 오류가 생기기 때문입니다.
- 채점기 출력이 실행 기록 계약을 만족하는지 명령줄로 연결해 검증했습니다.
- 탐지기 환경이 서지 않을 경우의 [축소 대안](../research/EXPERIMENT_DESIGN.md)을 결과 확인 전에 고정했습니다.

다운로드 도구의 검증과 별도로 독립 재검증을 수행했습니다. 확인 항목과 결과는 다음과 같습니다.

- 파일 크기가 [고정 입력](../config/study_inputs.json)의 `member_size`와 세 건 모두 일치합니다.
- SHA-256을 다시 계산해 manifest 기록과 일치함을 확인했습니다.
- 전체 JSON 행을 다시 파싱해 이벤트 수가 manifest와 일치함을 확인했습니다.
- **각 파일의 hostname이 단일 값이며 의도한 호스트와 일치합니다.** 바이트 오프셋으로 TAR 멤버를 잘라냈으므로 다른 호스트의 자료가 섞였는지 확인이 필요했습니다.
- 세 파일 모두 시간순 정렬 위반이 0건입니다. 평가 구간이 연속된 위치 범위로 대응됩니다.
- scenario-1·2의 로그는 해당 날짜 전체를 담고 있으나 **scenario-3은 14:38:13에서 끝납니다.** OpTC 수집 종료일이기 때문으로 보입니다. 평가 구간이 14:25에 끝나므로 구간 자체는 온전히 포함되지만 뒤 여유가 약 13분뿐입니다. 이 사실을 결과 해석과 한계에 반영합니다.

정상 로그는 12개 중 2개만 확보한 상태이며, 학습 2019-09-21과 검증 2019-09-22가 아직 남았습니다.

### 2026-09-10 — 라벨 확보와 재현성 문제 발견

정답 라벨 저장소를 고정 커밋으로 확보하고 세 파일의 SHA-256을 대조해 모두 일치를 확인했습니다. 그동안 건너뛰던 검증 테스트가 이제 실제로 실행됩니다.

처음 대조에서는 세 파일이 모두 불일치했는데, 원인은 라벨이 아니라 Git의 `core.autocrlf` 설정이었습니다. 저장소는 LF로 보관하지만 이 설정이 켜진 환경에서는 체크아웃할 때 CRLF로 바뀝니다. 줄바꿈을 되돌리면 세 파일 모두 정확히 일치했습니다.

그대로 두었다면 **같은 커밋을 받은 사람이 Linux에서는 검증에 성공하고 Windows에서는 실패**했을 것입니다. 재현 패키지를 제3자가 확인할 때 드러났을 문제라 지금 고쳤습니다. 해시 기준을 LF 정규화로 정의하고 [검증 도구](../scripts/verify_labels.py)와 테스트에 반영했습니다.

### 현재 막힌 일

- 공식 OpTC 원본은 Google Drive 할당량 초과를 반환합니다.
- Inria 서버가 잠깐 열렸다가 다시 닫혔습니다. 1KiB 범위 요청이 HTTP 206을 반환해 공격 호스트 3개를 순차 요청했으나 모두 503이었고, 직후에는 방금 성공했던 요청까지 503이 됐습니다. 짧은 시간에 대용량 요청을 연달아 보낸 것이 원인일 가능성을 배제할 수 없어 즉시 재시도하지 않습니다. 재시도 원칙은 [데이터 접근 기록](../research/DATA_ACCESS.md)에 정했습니다. 정상 로그도 12개 중 10개가 남았습니다.
- KAIROS를 실제로 호출하는 실행기는 아직 없습니다. 노드 점수를 받아 기록으로 바꾸는 채점기까지는 만들었고, 남은 것은 전처리·학습·추론을 호출하는 부분입니다. 데이터가 없어 지금은 검증할 수 없습니다.
- Docker 엔진이 연결되지 않아 고정된 Dockerfile 경로를 아직 쓸 수 없습니다.
- VRAM이 10GB입니다. 호스트별 6.7~9GB 전처리 자료를 다루기에 충분한지 확인하지 않았습니다.

실행 환경은 더 이상 막힌 일이 아닙니다. Windows 호스트를 재조회한 결과 메모리 31.9GiB, 여유 디스크 1,882GiB, PostgreSQL 18.3, GeForce RTX 3080을 사용할 수 있습니다. 이전에 기록한 "PostgreSQL·NVIDIA 미구성"은 WSL 쪽 조회 결과였습니다.

다음 재개 조건: Inria 서버가 복구되면 고정된 입력 범위에서 선택 다운로드를 재시도하고, 무유실 기준 실행부터 진행합니다.
