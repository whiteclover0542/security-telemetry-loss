## 확인한 수정 과정

배포 README는 원본 사건을 호스트·날짜별로 분리하고 timestamp로 정렬한 뒤 수정한다고 설명한다. 수정 코드의 주된 대상은 혼합된 고유 식별자다. 실제 코드에서는 잘못 연결된 사건의 `actorID` 또는 `objectID` 외에도 `ppid`, principal, image path, parent image path, user, SID와 일부 객체별 참조 필드를 대응되는 프로세스 정보로 바꿀 수 있다.

따라서 수정본은 단순한 파일 재정렬본이 아니다. provenance graph의 노드·간선 연결과 노드 속성이 달라질 수 있다. 주실험에서 수정본을 사용하면 입력 버전을 명시하고, 원본 버전에서 얻은 탐지 기준이나 그래프를 섞지 않는다.

## 확인한 호스트 라벨 과정

`host_darpapy.py`는 초기 정답 파일의 `(hostname, pid, 시작, 종료)` 구간으로 악성 사건을 판정한다. 악성 프로세스가 만든 자식 프로세스를 발견하면 이를 목록에 추가하고, 프로세스 종료 사건에서 무한 종료 구간을 갱신한다. 제공된 셸 스크립트는 목록이 더 이상 변하지 않을 때까지 반복한다.

제공 스크립트의 실제 조건은 다음과 같다.

| 시나리오 | 날짜 | 처리 호스트 | 시간 여유 |
| --- | --- | --- | --- |
| 1 | 2019-09-23 | 201 포함 17개 호스트 | 90초 |
| 2 | 2019-09-24 및 일부 2019-09-25 처리 | 501 포함 10개 호스트 | 90초 |
| 3 | 2019-09-25 | 51, 351 | 90초 |

Python 프로그램의 기본값은 10초지만, 결과 생성 셸 스크립트는 90초를 전달한다. 재현 시 기본값에 의존하지 않고 90초를 명시해야 한다.

라벨은 유실된 입력에서 다시 생성하면 안 된다. 자식 생성 사건이나 종료 사건의 삭제 여부에 따라 정답 자체가 달라질 수 있기 때문이다. 고정된 수정본 전체 입력에서 제공된 라벨을 검증하고 확정한 뒤 모든 유실 조건에 같은 사건 정답과 공격 사례 정의를 적용한다.

## 선정한 1차 공격 사례

PIDSMaker 설정과 Inria 라벨의 공통 핵심 호스트를 먼저 사용한다.

| 사례 | 날짜 | 핵심 호스트 | Inria TAR 멤버 크기 | 데이터 위치 확인 |
| --- | --- | --- | ---: | --- |
| 1 | 2019-09-23 | SysClient0201 | 260,533,164바이트 | 확인 완료 |
| 2 | 2019-09-24 | SysClient0501 | 252,545,116바이트 | 확인 완료 |
| 3 | 2019-09-25 | SysClient0051 | 141,878,906바이트 | 확인 완료 |

정확한 TAR 바이트 위치는 `data/inria_index/<날짜>/index.jsonl`에 기록된다. 이 디렉터리는 대용량 자료 작업용이며 Git에는 포함하지 않는다. 인덱스 생성 절차는 `scripts/index_inria_tar.py`로 재현한다.

재현에 필요한 파일 ID·압축 멤버 위치·크기·라벨 해시는 [고정 입력 설정](../config/study_inputs.json)에 보존했다.

이 세 호스트는 서로 다른 공격 시나리오의 핵심 호스트지만 전체 공격을 대표한다고 단정하지 않는다. 각 시나리오에는 다른 관련 호스트가 있으므로 1차 분석의 표본 수는 공격 사례 3개다. 30개 유실 시드는 독립 공격 표본 수를 늘리지 않는다.

## 현재 결정과 미확정 항목

- 데이터 후보는 Inria 수정본 v1.0으로 좁힌다. 공식 원본 Drive의 할당량 제한이 해제되면 동일 호스트의 원본과 비교 가능한지 별도로 검토한다.
- 라벨 후보는 같은 코드 버전의 `ground_truth_corrected_sc*_updated.csv`와 생성 규칙이다.
- 라벨의 개별 사건 ID 목록, 탐지 성공 판정, KAIROS 임계값은 아직 확정하지 않았다.
- 수정·라벨 코드는 내려받아 읽었으며 실행하지 않았다. 내려받은 파일의 경로·크기·SHA-256은 [manifest](correction_sources_manifest.json)에 있다.

## 라벨 파일 확보와 해시 검증

2026-09-10에 저장소를 고정 커밋 `644f41fb`로 확보하고 세 라벨 파일의 SHA-256을 [고정 입력](../config/study_inputs.json)과 대조했다. 세 건 모두 일치한다.

검증 과정에서 재현성 문제를 하나 발견했다. 처음 대조에서 세 파일이 모두 불일치했는데, 원인은 라벨 내용이 아니라 Git의 `core.autocrlf` 설정이었다. 저장소는 LF로 보관하지만 이 설정이 켜진 환경에서는 체크아웃 시 CRLF로 변환되어 파일 바이트가 달라진다. 줄바꿈을 LF로 되돌리면 세 파일 모두 고정 해시와 정확히 일치했다.

따라서 고정 해시는 **줄바꿈을 LF로 정규화한 바이트 기준**으로 정의하고, 이를 `scripts/verify_labels.py`와 단위 테스트에 반영했다. 그대로 두었다면 같은 커밋을 받은 사람이 Linux에서는 검증에 성공하고 Windows에서는 실패했을 것이다. 재현 패키지를 제3자가 검증할 때 드러났을 문제다.

## 다운로드 시도 기록

세 TAR 멤버의 정확한 위치를 찾은 후 전체 멤버 Range 요청을 했다. 세 동시 요청과 이후 호스트 051 단독 요청 모두 서버가 HTTP 503을 반환했다. 호스트 051 위치의 256KiB 요청도 HTTP 504 후 503을 반환했다. 실패한 요청은 원자료 확보로 계산하지 않는다. 앞서 TAR 시작점의 256KiB Range 요청과 README 다운로드는 성공했으므로 경로와 부분 다운로드 기능은 확인된 상태다.

다음 시도에서는 서버 상태가 회복된 뒤 한 파일씩 요청한다. 성공하면 `scripts/fetch_inria_members.py`가 응답 범위·크기·SHA-256을 확인하고 gzip 전체를 읽어 모든 JSON 행과 이벤트 수를 검증한다.
