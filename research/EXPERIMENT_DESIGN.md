- 상태: 실행 전 설계. 실제 로그 확보·정답 대응·탐지기 검증 전이며 본실험은 승인된 최종 설계로 간주하지 않는다.

## 비교 조건

| 항목 | 설계 |
| --- | --- |
| 독립변수 | 균등 무작위 삭제 / 시간순 연속 삭제 |
| 기준 조건 | 추가 삭제 0%. 원본 센서 로그의 완전성을 뜻하지 않는다. |
| 주비교 유실률 | 10%. 결과 확인 전 지정하며 1%, 5%, 20%는 보조 분석으로 구분한다. |
| 삭제 대상 범위 | 호스트-일 입력 파일 전체가 아니라 공격별 평가 구간에 해당하는 위치 범위 [selection_start, selection_end)로 한정한다. 범위는 `scripts/window_positions.py`가 고정 입력의 timestamp에서 산출하고 기록한다. 파일 자체는 자르지 않는다. 탐지기가 그래프를 만들 때 하루 전체 문맥이 필요하기 때문이다. |
| 삭제 수 | 평가 구간 이벤트 수 N에서 k=floor(N×유실률). 두 방식에 같은 k 적용, 실제 비율 k/N도 기록한다. |
| 반복 | 조건별 시드 0~29, 30회. 공격 구간마다 기준 1회 + 4개 비율×2개 방식×30회 = 241회. 세 사례 전체로는 723회이며 실행 자원 판단은 아래 실행 예산 절에 따른다. |
| 무작위 삭제 | 평가 구간의 N개 위치에서 k개를 비복원 균등 추출한다. |
| 연속 삭제 | 시작 인덱스를 평가 구간 안에서 균등 선택하고 연속 k개를 제거한다. 삭제 구간 전체가 평가 구간 안에 들어간다. k=0이면 삭제 없음. |
| 입력 순서 | 원본의 실제 시간 형식·정밀도를 확인한 후 UTC 시각, 이벤트 ID, 원본 파일·행 번호 순서로 고정한다. 동시각 동률 처리와 중복 이벤트 정책은 입력 manifest에 기록한다. |
| 고정 요소 | 데이터·정렬·전처리 알고리즘, 탐지기 가중치·임계값, 초기 상태, 평가 시간창, 삭제 개수 |
| 삭제 위치 선정 | 공격 정답을 전달하지 않는다. 정답은 평가와 사후 겹침 분석에만 사용한다. |
| 적용 위치 | 원본 이벤트에서 삭제한 뒤 살아남은 사건으로 노드 속성과 그래프를 재구축한다. 학습·검증 자료는 삭제하지 않는다. |
| A-v2 1차 지표 | 시드 간 라벨 노드 재현율의 표본표준편차. 효과는 EV=V(연속)−V(무작위)이며 양수이면 가설 방향이다. 심각 저하 시드 비율의 차이도 함께 본다. |
| A-v1 지표 | 무유실 기준 탐지 성공 사례에서 공격 사례 탐지율 감소. 효과는 Δ=(기준−연속)−(기준−무작위). 모든 라벨 공격에 대한 결과도 별도로 보관한다. |
| 공동 지표 | 고정 라벨 노드 재현율. 사례 탐지율은 라벨 노드 하나만 임계값을 넘어도 1이므로 주비교 유실률에서 포화될 수 있다. 포화 시 어느 지표로 결론을 내릴지는 [분석 계획](ANALYSIS_PLAN.md)에 결과 확인 전에 고정했다. |
| 보조 지표 | 정상 구간 시간당 오탐, 삭제 구간의 실제 시간 길이·공격 시간과의 겹침(`scripts/mask_overlap.py`), 가능하면 공격 추적 성능 |

## 데이터와 탐지기 확인 결과

PIDSMaker 코드를 `external/PIDSMaker`에 확보했다. 확인 버전은 `ae1e9fd42604c769c01b2eaed6fb7f65e27f3cac`이다. 외부 코드는 Git 추적에서 제외하며 이 버전과 출처로 복원한다.

- [공식 저장소](https://github.com/ubc-provenance/PIDSMaker): OpTC h201, h501, h051 세 데이터셋은 각각 공격 1건으로 소개된다.
- [설치 문서](https://ubc-provenance.github.io/PIDSMaker/ten-minute-install/): 압축 DB는 각각 약 2GB, 1.5GB, 1.7GB이고 복원 DB는 9GB, 6.7GB, 7.7GB이다. 복원 크기는 RAM 요구량과 같지 않으며 그래프·학습 산출물의 추가 공간도 필요하다.
- 코드 `pidsmaker/config/config.py`의 후보 공격 구간은 h201 9월 23일 11:23~13:25, h501 9월 24일 10:28~15:29, h051 9월 25일 10:29~14:25이다(2019년). 공식 정답과의 대조는 아직 남아 있으므로 확정 평가 구간으로 사용하지 않는다.
- **시간대는 확정했다.** 설정의 시간 문자열에는 시간대 표기가 없지만, 이 값을 소비하는 `pidsmaker/utils/utils.py`의 `datetime_to_ns_time_US`가 `pytz.timezone("US/Eastern")`으로 지역화한다. 2019년 9월의 US/Eastern은 EDT, 즉 UTC−04:00이며 OpTC eCAR timestamp의 오프셋과 같다. 따라서 h201 구간은 `2019-09-23T11:23:00-04:00`부터 `2019-09-23T13:25:00-04:00`까지로 해석한다. 구간 산출 도구에 오프셋을 반드시 적게 한 이유가 이것이며, 앞선 도구 확인도 이 해석으로 수행했다. 다만 해당 함수는 `mktime`으로 로컬 시간대를 한 번 경유하므로, 실행 호스트의 시간대에서 해당 시각이 모호해지는 경우(서머타임 전환 시점)에는 값이 어긋날 수 있다. 세 구간은 전환 시점과 무관하다.
- 공식 정답과 CSV 라벨의 생성 관계를 검증해야 한다. 세 호스트가 서로 독립적인 공격 캠페인인지도 아직 확인하지 않았다.
- 탐지기는 PIDSMaker의 KAIROS 구현(commit `ae1e9fd42604c769c01b2eaed6fb7f65e27f3cac`)으로 고정한다. 2019-09-19~21 정상 자료로 학습하고, 2019-09-22 정상 자료에서 `max_val_loss` 임계값을 한 번 산출해 모든 평가 조건에서 재사용한다. 세부 선택 근거와 중단 기준은 [탐지기 선택 기록](DETECTOR_SELECTION.md)에 있다.

### 전처리 속성에 남는 정보 문제

확인 버전의 `dataset_preprocessing/optc/create_database_optc.py`는 `save_nodes`에서 전체 입력의 속성을 모으고 `save_events`에서 이벤트를 별도로 저장한다. `build_default_graphs.py`는 event_table을 시간순으로 읽는다.

따라서 DB 이벤트 행만 제거하면 제거한 사건에서 얻은 경로·명령줄 속성이 노드 테이블에 남을 가능성이 있다. 주실험은 원본 이벤트 삭제 후 노드 속성도 다시 생성한다. 완전한 입력에서 만든 속성을 고정한 DB 삭제 실험을 수행한다면, 그것은 별도의 '속성이 보존된 간선 유실' 보조 실험으로 표시한다. 원본 사건 유실과 같은 것으로 해석하지 않는다.

## 표본 수와 통계

계산식, 집계 단위, 보고 범위는 [분석 계획](ANALYSIS_PLAN.md)에 고정한다.

30개 시드는 동일 공격에 적용한 유실 변동이다. 독립적인 공격 30개가 아니다. 먼저 각 공격별로 시드 평균 효과와 변동을 보고하고, 전체 효과는 공격 사례별 동일 가중 평균으로 보고한다.

공격·캠페인 독립성, 실제 확보한 사례 수, 탐지 성공 판정을 확인한 뒤 신뢰구간 계산법과 실질적 동등 범위를 결과 확인 전에 별도 확정한다. 3개 호스트만 확보할 경우 사례 밖의 일반화를 제한하며 시드 90개를 독립 공격 표본 90개로 사용하지 않는다. 현재 신뢰구간 절차·동등 범위는 확정하지 않았고 가설 검정 결과도 없다.

## 실행 예산과 축소 규칙

전체 설계는 사례 3개 × 241회 = 723회 실행이다. 변형 입력을 모두 보관하면 확보한 멤버 크기(260,533,164 / 252,545,116 / 141,878,906바이트) 기준으로 약 150GB가 필요하고, 여기에 복원 DB 약 23GB와 그래프·학습 산출물이 더해진다. 재조회한 Windows 호스트의 여유 디스크는 1,882GiB이므로 용량이 당장의 제약은 아니지만, 재생성 가능한 중간 산출물을 723개 남길 이유도 없다. 실행 시간은 1회당 소요를 아직 측정하지 못했으며 이것이 실제 제약이다.

- 변형 입력은 보관하지 않는다. 마스크와 적용 manifest의 SHA-256·이벤트 수만 남기면 같은 변형을 언제든 다시 만들 수 있으므로, 각 실행이 끝나면 변형 파일을 삭제하고 마스크·manifest·실행 기록만 보존한다. 삭제 대상은 재생성 가능한 중간 산출물뿐이며 실행 결과와 증거는 삭제하지 않는다.
- 변형 생성 자체의 소요를 확보한 09-19 로그(5,136,112건, 284MiB)에서 실측했다. 마스크 적용 1회가 약 120초(출력 269MiB), 겹침 측정 1회가 약 49초다. 변형 720개면 탐지기를 한 번도 돌리지 않은 상태에서 약 34시간이다. 두 단계 모두 변형끼리 독립이므로 병렬 실행할 수 있고, 탐지기 소요와 합산해 축소 단계를 판단한다.
- 무유실 기준 실행 1회에서 전처리·그래프 구성·추론의 실제 소요 시간과 디스크 사용량을 측정한다.
- 측정한 1회 소요를 `T`라 할 때 총 소요 추정은 `723 × T`이다. 이 값이 확보 가능한 실행 시간을 넘으면 아래 순서로만 축소한다. 이 순서는 결과를 보기 전에 고정한 것이며, 어느 조건이 유리하게 나왔는지에 따라 바꾸지 않는다.

| 단계 | 축소 내용 | 남는 설계 |
| --- | --- | --- |
| 1 | 보조 유실률 1%와 20%를 제외 | 주비교 10%와 보조 5%, 사례 3개 × 121회 = 363회 |
| 2 | 보조 유실률 5%도 제외 | 주비교 10%만, 사례 3개 × 61회 = 183회 |
| 3 | 시드를 0~29에서 0~9로 축소 | 주비교 10%, 사례 3개 × 21회 = 63회 |

시드를 줄이면 사례별 탐지율의 분해능이 30분의 1에서 10분의 1로 낮아진다. 축소를 적용하면 어느 단계까지 적용했는지와 그때의 측정값을 결과에 함께 기록한다. 축소해도 세 사례와 두 유실 방식, 무유실 기준은 유지한다. 이 셋 중 하나라도 포기해야 한다면 가설을 검증한 것으로 보고하지 않는다.

## 축소 대안과 중단 기준

주실험은 KAIROS 재생을 전제한다. 탐지기 환경이 끝내 서지 않거나 기준 실행이 중단 조건에 걸리면 무엇을 결과물로 삼을지 결과 확인 전에 정한다. 아래 순서로만 후퇴하며, 어느 조건이 유리해 보이는지에 따라 고르지 않는다.

| 단계 | 조건 | 결과물 | 주장할 수 있는 범위 |
| --- | --- | --- | --- |
| 0 | 주실험 성립 | KAIROS 재생으로 A-v2·A-v1 검증 | 고정한 세 사례·탐지기·유실률 안에서의 관찰 |
| 1 | 무유실 기준에서 세 사례를 모두 탐지하지 못함 | 기준 실행 실패 기록과 그 원인 분석 | 이 탐지기로는 가설을 시험할 수 없었다는 결과. 가설의 참거짓은 주장하지 않는다 |
| 2 | 탐지기 환경이 서지 않음 | 입력 손상 측정만 수행. 유실 조건별로 공격 라벨 노드·간선의 소실 비율과 라벨 프로세스 경로의 단절 여부를 원본 대비로 계산 | 유실이 증거 자체를 얼마나 지우는지. 탐지 성능은 주장하지 않는다 |
| 3 | 위도 불가 | 도구·설계·측정 계획과 실패 기록 | 방법과 실패 사유. 가설 검증은 하지 않았다고 명시 |

단계 2는 탐지기 없이도 수행할 수 있고 이미 만든 도구로 계산한다. 유실 마스크와 고정 라벨만 있으면 되기 때문이다. 이 경우에도 A-v2의 변동 비교는 성립한다. 종속변수가 탐지 결과에서 증거 소실로 바뀔 뿐이며, 그 사실을 결과와 결론에 명시한다.

어느 단계로 후퇴하든 세 사례, 두 유실 방식, 무유실 기준은 유지한다. 후퇴 사유와 시점은 아래 변경 기록에 남긴다.

## 실행 환경과 접근 확인

최초 조회는 Ubuntu(WSL) 쪽에서 수행했고 `psql`과 `nvidia-smi`를 PATH에서 찾지 못했다. 그때도 물리 GPU 부재를 확정하지는 않았다. 2026-09-10 Windows 호스트에서 `scripts/check_experiment_environment.py`로 다시 조회한 결과는 다르다.

| 항목 | Ubuntu(WSL) 최초 조회 | Windows 호스트 재조회 |
| --- | --- | --- |
| 메모리 | 7,859MiB | 31.9GiB |
| 디스크 여유 | 약 337GB | 1,882GiB |
| PostgreSQL | PATH에서 미발견 | psql 18.3 |
| NVIDIA | PATH에서 미발견 | GeForce RTX 3080, 10,240MiB, 드라이버 591.86 |
| Docker | 엔진 연결 실패 | 엔진 연결 실패(종료 코드 1) |

따라서 "PostgreSQL과 GPU가 없다"는 이전 기록은 Windows 호스트에는 해당하지 않는다. 남은 실행 관문은 다음과 같다.

- VRAM이 10,240MiB다. PIDSMaker의 OpTC 전처리 자료는 호스트별 6.7~9GB이며, 이 구성이 10GB VRAM에 들어가는지는 확인하지 않았다.
- Docker 엔진이 연결되지 않아 고정된 Dockerfile 경로를 아직 쓸 수 없다.
- 재조회 호스트의 Python은 3.11.9다. PIDSMaker Dockerfile은 Python 3.9와 Torch 1.13.1 CUDA 11.7 구성을 사용하므로 현재 Python에 그대로 설치했다고 가정하지 않는다.

이 조회는 도구·메모리·디스크의 존재를 확인한 것이며 KAIROS 실행 성공을 뜻하지 않는다.

공식 README·스키마·정오표는 HTTP 200으로 확보했다. 원본 공개 폴더에는 `AIA-51-75.ecar-last.json.gz`가 표시되었으나 파일 요청은 HTTP 200의 **Quota exceeded HTML**을 반환했다. DB h501 링크는 바이러스 검사 불가 확인 HTML을 반환했다. 어느 응답도 실제 로그나 PostgreSQL 덤프 확보로 계산하지 않는다.

출처·확인 시간·응답 유형·저장 바이트·SHA-256은 [접근 확인 기록](source_checks/20260910T005048434081Z/manifest.json)에 있다. 저장된 `.sample`은 문서·웹 응답이며 실험 원자료가 아니다. 할당량 초과를 우회하지 않고, 해제 후 재시도하거나 공식 제공 파일을 별도로 확보한다.

## 구현과 검증

`scripts/loss_masks.py`는 고정된 순서의 이벤트 위치와 평가 구간을 받아 삭제 인덱스를 만든다. 공격 라벨을 입력받지 않으며 입력 SHA-256·구간·시드·Python 버전·삭제 개수를 기록하고 기존 출력 덮어쓰기를 거부한다. `scripts/apply_loss_mask.py`는 해당 마스크를 JSONL 또는 JSONL.GZ 스트림에 적용하고, 입력·마스크·출력 SHA-256과 전후 이벤트 수를 manifest에 남기며 구간을 벗어난 마스크를 거부한다. `scripts/window_positions.py`는 평가 구간을 파일 내 위치로 변환하고, `scripts/mask_overlap.py`는 마스크가 실제로 지운 시간 길이와 공격 구간 겹침을 측정한다. `scripts/aggregate_results.py`는 실행 기록에서 사전 고정한 R·L·E와 RC·LC·EC를 계산한다. 어느 도구도 탐지기 속성 재구축·KAIROS 실행기는 수행하지 않는다.

실제 데이터 확보부터 결과 재확인까지의 순서는 [실행 절차](RUNBOOK.md)에 정리한다.

```powershell
python -m unittest discover -s tests -v
python scripts/loss_masks.py --help
python scripts/probe_sources.py
```

앞의 두 명령은 오프라인 검증이고 마지막 명령은 네트워크 접근 확인이다. 45개 단위 테스트가 통과했다(1개는 저장소에 포함하지 않은 외부 코드가 있을 때만 실행). 계획한 비율·시드와 경계 크기를 조합한 조건에서 개수, 중복 없음, 범위, 연속성을 검증했고, 두 방식이 같은 구간에서 같은 개수를 지우는지, 구간 산출이 창 경계와 정렬 위반을 바르게 다루는지, 집계가 계약 위반 기록을 거부하고 포화를 판정하는지도 확인했다.

단위 테스트는 함수 단위이므로 명령줄 진입점과 도구 사이의 연결을 따로 실행해 확인했다. 구간 산출 → 마스크 생성 → 마스크 적용 → 겹침 측정 → 집계를 명령줄로 이어 실행했고, 두 유실 방식이 평가 구간에서 같은 개수를 지우고 삭제가 구간을 벗어나지 않으며 삭제 구간의 시간 길이만 달라지는 것을 확인했다.

같은 순서를 확보한 09-19 로그(5,136,112건)에도 적용했다. 122분 창에서 두 방식 모두 52,474건(창의 10.0%)을 창 안에서만 삭제했고, 연속 삭제의 실제 시간 길이는 564.6초였다. 즉 10% 연속 유실은 평가 구간 122분 중 약 9.4분에 해당하며 나머지 약 92%의 시간은 손상되지 않는다. 이는 도구 동작 확인에서 측정한 값이며, 09-19는 정상 자료이므로 탐지 결과와 무관하다.

이는 도구가 설계대로 동작하는지 확인한 것이며, 탐지기 실행이나 가설 검증이 아니다. 09-19는 정상 자료이므로 공격 탐지 결과와 무관하다.

## 본실험 시작 전 필요한 항목

추가 접근 조사: [데이터 접근 확인](DATA_ACCESS.md). 공식 원본 추가 4개도 제한되었지만 Inria 수정본은 Windows curl로 256KiB를 수신하여 eCAR 1,837건을 파싱했다. 이는 호스트 269의 불완전한 표본이며 주실험 입력 확정이나 공격 탐지 실행은 아니다.

수정·라벨 검토: [Inria OpTC 수정·라벨 검토](LABEL_AND_CORRECTION_REVIEW.md). 1차 사례는 서로 다른 세 시나리오의 핵심 호스트 201·501·051로 좁혔다. 제공된 호스트 라벨 생성은 90초 여유를 명시하고 자식 프로세스를 반복 추적한다. 정답은 유실 전 입력에서 고정하여 모든 조건에 동일하게 적용한다.

1. 원본 표본과 전체 선정 구간 파일 확보, 압축 무결성·실제 스키마·출처·체크섬 검증.
2. 공식 정답과 사건·호스트·UTC 구간 대응, 포함/제외 목록 확정.
3. 원본 파서 및 유실 후 속성 재구축 구현, 남은 이벤트에 삭제 사건의 정보가 들어가지 않는지 확인.
4. 탐지기 환경·버전·가중치·임계값·초기 상태·정상 검증 구간 고정.
5. 탐지 성공 기준, 독립 표본 단위, 통계 절차·동등 범위 확정.
6. 무유실 시험 1회로 메모리·시간·출력·오탐을 확인하고 실행 자원 선택.
7. 설계 버전과 manifest를 보존한 뒤 본실험 실행. 결과에 맞춘 사례·임계값 선택은 하지 않는다.

### 탐지 판정과 기준 실행 중단 조건

- 사례 탐지: 고정한 수정 라벨에 속한 노드 중 하나 이상이 고정 검증 임계값을 **초과**하면 해당 공격 사례를 탐지한 것으로 판정한다.
- 무유실 기준 실행에서 세 주 사례 각각이 위 조건을 충족해야 유실 비교를 시작한다.
- 하나라도 탐지하지 못하면 유실 때문에 감소한 탐지율을 정의할 수 없으므로 결과를 버리거나 탐지기를 사후 조정하지 않고 실험을 중단한다. 이 경우 KAIROS가 본 가설을 시험할 수 없었다고 기록한다.
- 모든 반복은 같은 체크포인트와 같은 초기 추론 상태에서 시작한다. 라벨, 임계값, 사례 분모는 삭제된 입력에 맞춰 다시 계산하지 않는다.

각 실행은 입력/코드/가중치 해시, 구간, 시드, 요청·실제 유실률, 삭제 마스크, 기준·변형 탐지 결과, 경보, 시작·종료 시각, 오류를 남긴다. 실패한 실행도 삭제하지 않는다.

- 2026-09-10: PIDSMaker KAIROS를 주 탐지기로 고정했다. 원 OpTC KAIROS 노트북은 테스트 창마다 임계값을 다시 산출하고, PIDSMaker 큐 평가는 미작동 표시가 있어 주평가에서 제외했다. 정상 학습일 2019-09-19~21, 검증일 2019-09-22, `max_val_loss` 임계값과 무유실 기준 중단 조건은 결과 확인 전에 고정했다.
- 2026-09-10: 유실 마스크 생성기만 있던 절차에 JSONL/gzip 적용기와 실행 절차를 추가했다. 이유는 각 변형의 입력·마스크·출력 해시와 이벤트 수를 보존하고, 실제 로그가 준비됐을 때 동일한 순서로 재실행하기 위해서다.
- 2026-09-10: 검토에서 삭제 범위가 호스트-일 파일 전체로 잡혀 있음을 확인하고 평가 구간으로 한정했다. 확보한 SysClient0201 2019-09-19 로그(5,136,112건)에 2시간 2분 창을 적용해 실측하면 구간 이벤트는 524,744건으로 하루의 10.2%다. 이전 설계의 연속 삭제는 하루의 10%인 513,611건을 하루 전체에서 균등한 시작점으로 지우므로, **시드의 77.5%가 평가 구간에서 단 한 건도 지우지 않는다.** 남은 22.5%는 구간의 절반 가까이를 한꺼번에 지운다. 반면 무작위 삭제는 모든 시드가 구간 안에서 10%를 지운다. 즉 두 방식이 평가 구간에서 제거하는 이벤트 수가 시드마다 달라져 같은 삭제 개수를 전제한 가설을 검증할 수 없고, 연속 조건의 대부분이 사실상 무유실 실행이 되어 효과가 가설과 반대 방향으로 치우친다. 구간을 한정하면 두 방식 모두 매 시드마다 정확히 52,474건(구간의 10.0%)을 지운다. 마스크 스키마를 `loss-mask-v2`로 올리고 구간 산출·겹침 측정 도구를 추가했다. 가설 A-v1은 유지한다. 이 수정은 실험 결과를 보기 전에 이루어졌으며 어떤 조건의 결과도 존재하지 않는다.
- 2026-09-10: 사례 탐지율의 포화 가능성을 확인하고 고정 라벨 노드 재현율을 공동 1차 지표로 추가했다. 포화 시 어느 지표로 결론을 내릴지의 순서도 결과 확인 전에 고정했다. 실험 결과는 아직 없다.
- 2026-09-10: 723회 실행의 저장 용량과 소요 시간을 산출하지 않았음을 확인하고, 변형 입력 비보관 원칙과 단계별 축소 규칙을 결과 확인 전에 고정했다.
- 2026-09-10: 가설을 A-v1에서 A-v2로 수정했다. 도구 확인 과정에서 10% 연속 유실의 실제 삭제 길이가 122분 창 중 9.4분이고 창의 약 92%가 손상되지 않는다는 것을 측정했다. 연속 유실은 평균적으로 증거를 더 지우는 것이 아니라 결정적 단계에 떨어질 때만 치명적인 복불복에 가깝다. 종속변수를 평균 탐지율 차이에서 시드 간 변동으로 바꾸면 인용 문헌 [3]의 "어느 레코드가 사라지느냐가 결과를 가른다"와도 직접 연결되고, 독립 표본이 아닌 시드 30개가 한계가 아니라 측정 수단이 된다. A-v1의 평균 비교는 폐기하지 않고 함께 사전 등록해 모두 보고한다. 추가 실행은 필요하지 않다. 이 수정은 어떤 탐지 결과도 없는 상태에서 이루어졌다.
